Quase tudo no projeto acontece em três arquivos: [main.cpp](src/main.cpp), [shader_vertex.glsl](src/shader_vertex.glsl) e [shader_fragment.glsl](src/shader_fragment.glsl). Antes de começar: por enquanto o código ainda é a base do professor (esfera, coelho e plano), não o Hasty Wings. Mas o jogo vai gerar imagens pelo mesmo caminho, então tudo abaixo continua valendo.

## Visão geral: rasterização (Aula 03)

A Aula 03 compara dois algoritmos de rendering: **Ray Casting** e **Rasterização**. O projeto usa rasterização, que é o que o OpenGL faz:

```
for object in scene
  for pixel covered by object
    "pixel color = object color"
```

No código, o `for object in scene` são as três chamadas `DrawVirtualObject(...)` dentro do loop principal ([main.cpp:338-458](src/main.cpp#L338-L458)). Esse loop roda uma vez por quadro e segue as etapas do **Pipeline Gráfico** dos slides:

**Aplicação → Geometria (Model/View, Vertex Shading, Projeção, Clipping, Screen Mapping) → Rasterização → Imagem (framebuffer)**

## 1. Aplicação: modelagem geométrica (Aula 04)

Os objetos são **malhas de triângulos** lidas de arquivos `.obj` (`ObjModel spheremodel("../../data/sphere.obj")`, [main.cpp:306](src/main.cpp#L306)).

- **Normais por vértice**: se o arquivo não traz normais, `ComputeNormals()` ([main.cpp:630](src/main.cpp#L630)) calcula a normal de cada triângulo com o produto vetorial `(b−a)×(c−a)`. Depois tira a média das normais de todos os triângulos que tocam cada vértice, que é o método de Gouraud.
- **Envio para a GPU**: `BuildTrianglesAndAddToVirtualScene()` ([main.cpp:747](src/main.cpp#L747)) coloca posições, normais e coordenadas de textura em **VBOs** e organiza tudo num **VAO**. As posições vão em coordenadas homogêneas `(x,y,z,1)` e as normais como vetores `(x,y,z,0)`, como nos Fundamentos Matemáticos (Aula 02).

## 2. Model Matrix: Model Coords → World Coords (Aulas 06/07 e 08)

Cada objeto recebe uma **matriz de modelagem** feita de translações e rotações, por exemplo a esfera ([main.cpp:418](src/main.cpp#L418)):

```cpp
model = Matrix_Translate(-1,0,0) * Matrix_Rotate_Z(0.6) * Matrix_Rotate_X(0.2) * Matrix_Rotate_Y(...);
```

As transformações valem **da direita para a esquerda**: primeiro gira em Y, depois em X e em Z, e por último translada. A Aula 08 mostra que isso é uma **mudança de sistema de coordenadas**, do sistema local do objeto para o sistema global (World). O tempo (`glfwGetTime()`) entra no ângulo de rotação, e por isso os objetos giram sozinhos.

## 3. View Matrix: World → Camera Coords (Aula 08)

A câmera é do tipo **look-at**. A posição `c` sai de **coordenadas esféricas** (`r`, `θ`, `φ`, controladas pelo mouse), e a câmera olha sempre para a origem ([main.cpp:361-374](src/main.cpp#L361-L374)).

`Matrix_Camera_View()` ([matrices.h:224](include/matrices.h#L224)) monta a base da câmera igual aos slides:
- `w = −view` (a câmera olha para −w)
- `u = up × w`, depois normalizado
- `v = w × u`

A matriz tem `u`, `v` e `w` como linhas e `−u·(c−o)` etc. na última coluna. Ela escreve qualquer ponto do mundo nas coordenadas da câmera.

## 4. Projeção: Camera → Clip → NDC (Aula 09)

O código tem as duas **projeções planares** da Aula 09, e as teclas P/O trocam entre elas:

- **Ortográfica** (`Matrix_Orthographic`): leva a caixa `[l,r]×[b,t]×[f,n]` para o cubo `[−1,1]³`. Preserva paralelismo e tamanhos relativos.
- **Perspectiva** (`Matrix_Perspective`, [matrices.h:269](include/matrices.h#L269)): aplica a matriz **P** (com `n`, `n+f`, `−fn` e o `1` na última linha, que copia z para w) e depois a ortográfica **M**. O resultado é `−M·P`. O sinal negativo deixa `w > 0`, porque a GPU testa o clipping como `−w ≤ x ≤ w` antes da divisão (o comentário no código explica bem). O FOV é π/3, e `near = −0.1`, `far = −10` são negativos porque a câmera olha para −z.

No vertex shader, cada vértice passa por toda a cadeia:

```glsl
gl_Position = projection * view * model * model_coefficients;
```

Depois disso a própria GPU faz o **clipping**, descartando o que fica fora do **frustum**, e a **divisão por w**, que dá as NDC. É essa divisão que deixa menores os objetos mais longe.

## 5. Screen Mapping (Viewport)

`glViewport(0, 0, width, height)` ([main.cpp:1053](src/main.cpp#L1053)) leva as NDC `[−1,1]` para coordenadas de pixel da janela.

## 6. Rasterização, Z-buffer e Culling (Aulas 03 e 09)

- O rasterizador encontra os pixels que cada triângulo cobre e **interpola** os valores `out` do vertex shader (`position_world`, `normal`, `texcoords`), gerando um valor por **fragmento**.
- **Z-buffer** (`glEnable(GL_DEPTH_TEST)`): quando dois objetos caem no mesmo pixel, fica o mais próximo da câmera. É o "pixel color = closest object color" dos slides.
- **Backface culling** (`GL_CULL_FACE`, `GL_CCW`): triângulos de costas para a câmera nem são desenhados.

## 7. Fragment Shader: cor de cada pixel (Aulas 17/18 e 20/21)

### Texturas (Aula 20)
A **refletância difusa Kd** muda de ponto para ponto, porque é lida de uma imagem. Cada objeto usa uma **função de parametrização φ(p) = (u,v)** diferente:

| Objeto | Parametrização | Código |
|---|---|---|
| Esfera | **Projeção esférica**: `θ = atan(x,z)`, `φ = asin(y/ρ)`, normalizados para [0,1] | [shader_fragment.glsl:62-82](src/shader_fragment.glsl#L62-L82) |
| Coelho | **Projeção planar XY**: `u` e `v` são x e y normalizados pela bounding box (AABB) | [shader_fragment.glsl:83-111](src/shader_fragment.glsl#L83-L111) |
| Plano | Coordenadas de textura que já vêm no `.obj` | [shader_fragment.glsl:112-120](src/shader_fragment.glsl#L112-L120) |

As duas primeiras usam `position_model`, ou seja, **coordenadas do modelo**. Assim a textura acompanha o objeto quando ele gira. Em `LoadTextureImage()` ([main.cpp:473](src/main.cpp#L473)) aparecem os conceitos de amostragem da Aula 20/21: **wrapping** (`CLAMP_TO_EDGE`), **mipmapping** (`glGenerateMipmap`) e filtragem **trilinear** (`LINEAR_MIPMAP_LINEAR`) para a minificação e **bilinear** para a magnificação.

### Iluminação (Aulas 17/18)
Por enquanto o modelo é só **Lambert** (termo difuso), com um **termo ambiente** bem pequeno:

```glsl
float lambert = max(0, dot(n, l));      // cos θ entre normal e luz
color.rgb = Kd0 * (lambert + 0.01);
```

- `l = (1,1,0)` é uma luz direcional fixa.
- A normal vai para o mundo com a **inversa da transposta** da matriz model ([shader_vertex.glsl:58](src/shader_vertex.glsl#L58)). Isso mantém a normal perpendicular à superfície mesmo com escalas não uniformes (Aula 07).
- A iluminação é calculada **por fragmento**, com a normal interpolada. É o **Phong shading** (interpolação de normais), diferente do **Gouraud shading**, que calcula a cor nos vértices e interpola a cor.
- O shader já calcula `v` (o vetor até a câmera), mas ainda não usa. Ele seria usado para acrescentar o **termo especular** (Phong ou Blinn-Phong: `ks·I·max(0, r·v)^q`) e chegar à equação completa da Aula 17/18.

### Correção gamma
No final, `pow(color, 1/2.2)` converte a cor do espaço linear para **sRGB** do monitor. As texturas são carregadas como `GL_SRGB8`, então a GPU faz a conversão contrária na leitura. Com isso, toda a conta de iluminação acontece em espaço linear.

## 8. Imagem final

O resultado vai para o **framebuffer**. `glfwSwapBuffers()` faz o **double buffering**: o quadro é desenhado num buffer escondido e só depois trocado com o da tela, o que evita *tearing*.

----- CLAUDE [2026-11-01 12:36:43] -----
Sim. `Matrix_Translate(-1, 0, 0)` coloca a esfera 1 unidade à esquerda da origem do mundo. O centro dela, que no próprio modelo fica em (0,0,0), vai parar em (−1, 0, 0) no mundo.

As três rotações orientam a esfera. Leia o produto **da direita para a esquerda**, porque essa é a ordem em que as matrizes agem no vértice:

```
p_mundo = T · Rz · Rx · Ry · p_modelo
```

1. **`Rotate_Y(g_AngleY + tempo*0.1)`** faz a esfera **girar em torno do próprio eixo vertical**. O ângulo cresce com o tempo, por isso ela fica girando sozinha. O `g_AngleY` é um ajuste manual que você controla pelo teclado.
2. **`Rotate_X(0.2)`** e **`Rotate_Z(0.6)`** são ângulos fixos que **inclinam esse eixo de giro**, como a inclinação do eixo da Terra. Sem eles a esfera giraria em pé. Com eles, gira em torno de um eixo torto.
3. **`Translate`** vem por último e só leva a esfera já orientada até a posição final.

Dois detalhes:

- **A ordem importa.** Todas as rotações acontecem com a esfera ainda centrada na origem, então ela gira **em torno do próprio centro**. Se a translação viesse antes (mais à direita no produto), a esfera primeiro iria para (−1,0,0) e depois giraria em torno da origem do mundo. Aí ela **orbitaria** a origem em vez de girar no lugar.
- **A rotação só aparece por causa da textura.** Uma esfera parece igual em qualquer orientação. O que mostra o giro são os tijolos, porque a textura usa `position_model`, ou seja, fica presa às coordenadas do objeto.

As duas linhas seguintes não criam matrizes. `glUniformMatrix4fv` envia a `model` para o vertex shader, e `glUniform1i(..., SPHERE)` avisa o fragment shader que o objeto é a esfera, para ele escolher a projeção esférica da textura. Só então `DrawVirtualObject` desenha os triângulos.

3. Todos os vértices da esfera são transformados de novo, a partir das coordenadas originais do `.obj`.

A diferença é que **só o ângulo do `Rotate_Y` muda entre um quadro e outro**:

| Matriz | Valor a cada quadro |
|---|---|
| `Translate(-1,0,0)` | sempre igual |
| `Rotate_Z(0.6)` | sempre igual |
| `Rotate_X(0.2)` | sempre igual |
| `Rotate_Y(g_AngleY + t*0.1)` | ângulo diferente, porque `t` cresce |

Então o efeito *parece* um posicionamento inicial fixo com um giro contínuo. Por baixo, porém, tudo é refeito a cada quadro.

O mapeamento de texturas ocorre so na inicializacao do programa ou ele repete por frame?

----- CLAUDE [2026-11-01 12:41:28] -----
Depende da parte. O carregamento da imagem acontece **uma vez só**, mas o mapeamento em si se repete **em todo quadro, para cada fragmento**.

## Uma vez, na inicialização

`LoadTextureImage()` ([main.cpp:302-303](src/main.cpp#L302-L303)) é chamada antes do loop e faz três coisas:
- lê o `.jpg` do disco (`stbi_load`);
- envia a imagem para a memória da GPU (`glTexImage2D`);
- gera os mipmaps (`glGenerateMipmap`) e configura o sampler (wrapping e filtragem).

Daí em diante a imagem fica guardada na GPU e não é mais lida do disco.

As coordenadas `(u,v)` **do plano** também são enviadas uma vez só. Elas vêm do `.obj` e vão para um VBO em `BuildTrianglesAndAddToVirtualScene()`, junto com as posições e as normais.

## Todo quadro, em cada fragmento

O fragment shader roda **para cada pixel coberto por um objeto, em todo quadro**. Cada execução faz:

1. **Calcula `(u,v)`**: a projeção esférica (esfera) ou planar (coelho) a partir de `position_model`. No plano, ele só lê o `texcoords` interpolado.
2. **Amostra a textura**: `texture(TextureImage0, vec2(U,V))` busca a cor na imagem. O filtro trilinear escolhe o nível de mipmap e mistura os texels vizinhos.
3. **Usa essa cor como `Kd`** na equação de Lambert.

Ou seja, a função de parametrização φ(p) = (u,v) da Aula 20 é calculada de novo milhões de vezes por segundo. Isso é barato para a GPU, que roda milhares de fragmentos em paralelo.

## Por que precisa refazer

O nível de mipmap depende do tamanho que o objeto ocupa na tela. Quando você aproxima ou afasta a câmera, a amostragem muda, então ela precisa ser refeita a cada quadro. Já as coordenadas `(u,v)` de um ponto da esfera nunca mudam, porque são calculadas em coordenadas do modelo. Dava para calcular uma vez e guardar num VBO, como o plano faz. O código calcula no shader porque é o exercício do laboratório: implementar as projeções esférica e planar.

E se acontece uma mudanca de textura em tempo real?

----- CLAUDE [2026-11-01 13:42:07] -----
Depende do tipo de mudança. Há quatro jeitos comuns, do mais simples ao mais caro:

## 1. Trocar entre texturas já carregadas (o mais comum)

Você carrega todas as imagens na inicialização, cada uma numa *texture unit* (`TextureImage0`, `1`, `2`...), e escolhe qual usar no momento de desenhar. No projeto isso já acontece por objeto: o shader usa `TextureImage0` para esfera e coelho e `TextureImage1` para o plano, decidindo pelo `object_id`.

Para trocar em tempo real, basta mandar um uniform novo todo quadro:

```cpp
// main.cpp, no loop
glUniform1i(g_skin_uniform, jogador_pegou_powerup ? 1 : 0);
```

```glsl
// fragment shader
Kd0 = (skin == 1) ? texture(TextureImage2, uv).rgb
                  : texture(TextureImage0, uv).rgb;
```

Não há custo de upload, porque as imagens já estão na GPU. Trocar é só mudar um número.

## 2. Mexer nas coordenadas `(u,v)` (textura "animada")

A imagem continua a mesma, e o que muda é **onde** ela é amostrada. Por exemplo, mandar o tempo como uniform e deslocar o `u`:

```glsl
Kd0 = texture(TextureImage1, vec2(U + tempo*0.1, V)).rgb;
```

Com isso a textura "escorre" pela superfície, o que serve para água, nuvens ou lava. Para repetir sem cortes, o wrapping precisa ser `GL_REPEAT`. Hoje está `CLAMP_TO_EDGE` ([main.cpp:497-498](src/main.cpp#L497-L498)), e com ele a borda da imagem ficaria esticada.

## 3. Misturar texturas ou mudar a cor por código

Dá para combinar duas texturas com `mix(texA, texB, t)`, com o `t` vindo de um uniform. Também dá para multiplicar a cor por um fator. A imagem continua a mesma, e o shader decide a cor final.

## 4. Alterar os pixels da imagem na GPU (o mais caro)

Se o conteúdo da imagem realmente muda, como num vídeo ou numa imagem gerada pela CPU a cada quadro, você reenvia os pixels com `glTexSubImage2D`. Funciona, mas copiar dados da CPU para a GPU todo quadro é lento. Por isso só vale quando não há alternativa, e é raro num jogo como o de vocês.

---

**No Hasty Wings**, a mecânica do pôr do sol se encaixa bem nos itens 2 e 3. Você manda um uniform `hora_do_dia` (0 = meio-dia, 1 = noite) e usa ele para:
- misturar a cor do céu de azul para laranja e depois escuro (`mix`);
- mudar a cor e a direção da luz `l`, que hoje é fixa em `(1,1,0)` no shader.

Assim o cenário inteiro escurece conforme o jogador perde velocidade, sem carregar nenhuma imagem nova.

----- CLAUDE [2026-11-01 13:43:26] -----
Imagino que a pergunta seja sobre a `LoadShadersFromFiles()` ([main.cpp:560](src/main.cpp#L560)). Ela **pega os dois arquivos `.glsl`, compila e monta com eles o "programa de GPU"**, que é o que roda nas etapas programáveis do pipeline (Vertex Shading e Fragment Shading, Aula 03).

## Passo a passo

**1. Lê e compila cada shader** (`LoadShader_Vertex` / `LoadShader_Fragment` → `LoadShader`, [main.cpp:925](src/main.cpp#L925))
- Lê o arquivo de texto (`../../src/shader_vertex.glsl`, por exemplo).
- `glShaderSource` entrega o código-fonte ao driver da placa de vídeo.
- `glCompileShader` compila o GLSL para o código de máquina da **sua** GPU. Por isso os shaders são compilados enquanto o programa roda, e não junto com o C++: cada placa tem um código de máquina diferente.
- Se houver erro de sintaxe no GLSL, o log aparece no terminal (`ERROR: OpenGL compilation of ... failed`).

**2. Junta os dois num programa** (`CreateGpuProgram`, [main.cpp:995](src/main.cpp#L995))
- `glAttachShader` + `glLinkProgram` ligam o vertex shader ao fragment shader. É no *link* que o OpenGL confere se cada `out` do vertex shader (`position_world`, `normal`, `texcoords`...) tem um `in` com o mesmo nome no fragment shader.
- O ID do programa fica guardado em `g_GpuProgramID`, e o loop principal usa ele com `glUseProgram(g_GpuProgramID)`.

**3. Pega os "endereços" dos uniforms**
```cpp
g_model_uniform = glGetUniformLocation(g_GpuProgramID, "model");
```
Isso busca onde está a variável `uniform mat4 model` dentro do programa compilado. Esses endereços são os que o loop usa depois com `glUniformMatrix4fv(g_model_uniform, ...)` para mandar as matrizes todo quadro. É a ponte entre as variáveis do C++ e as do GLSL.

**4. Liga os samplers às texture units**
```cpp
glUniform1i(glGetUniformLocation(g_GpuProgramID, "TextureImage0"), 0);
```
Isso diz que `TextureImage0` no shader lê da texture unit 0, onde `LoadTextureImage` colocou a primeira imagem (tijolos). `TextureImage1` lê da unit 1 (pedras), e assim por diante.

## Quando é chamada

- **Uma vez na inicialização** ([main.cpp:299](src/main.cpp#L299)).
- **Toda vez que você aperta R** ([main.cpp:1280](src/main.cpp#L1280)). Por isso ela começa apagando o programa anterior (`glDeleteProgram`). Dá para editar o `shader_fragment.glsl`, salvar, apertar R e ver a mudança na hora, sem recompilar nem reiniciar o programa. Isso ajuda muito quando vocês forem ajustar a iluminação ou o céu do Hasty Wings.

Se você adicionar um uniform novo, como o `hora_do_dia` do pôr do sol, precisa acrescentar o `glGetUniformLocation` correspondente nessa função.

## 1. Model & View

**Model** (coordenadas do modelo → mundo): para cada objeto, o loop monta uma matriz com translações e rotações e envia para a GPU antes de desenhar:
```cpp
model = Matrix_Translate(-1,0,0) * Matrix_Rotate_Z(0.6) * Matrix_Rotate_X(0.2) * Matrix_Rotate_Y(...);
glUniformMatrix4fv(g_model_uniform, 1, GL_FALSE, glm::value_ptr(model));
```

**View** (mundo → câmera): a posição `c` da câmera sai de coordenadas esféricas (mouse), e `Matrix_Camera_View(c, view, up)` monta a base `u, v, w`:
- `w = −view`, `u = up × w`, `v = w × u`
- a matriz é `[u; v; w]` com a translação `−u·(c−o)`, `−v·(c−o)`, `−w·(c−o)`

A `view` é enviada **uma vez por quadro**, porque é igual para todos os objetos. A `model` é enviada **uma vez por objeto**.

## 2. Vertex Shading

[shader_vertex.glsl](src/shader_vertex.glsl) roda **uma vez para cada vértice** de cada objeto desenhado:

```glsl
gl_Position    = projection * view * model * model_coefficients;  // para o clipping
position_world = model * model_coefficients;                      // para a iluminação
position_model = model_coefficients;                              // para a textura (esfera/coelho)
normal         = inverse(transpose(model)) * normal_coefficients; // normal no mundo
normal.w = 0.0;
texcoords      = texture_coefficients;                            // (u,v) do .obj
```

Os dados de entrada (`layout(location=0,1,2)`) são os VBOs que `BuildTrianglesAndAddToVirtualScene()` enviou para a GPU na inicialização. Aqui é **só transformação**: nenhuma cor é calculada. A iluminação ficou toda no fragment shader, e é isso que faz dele um Phong shading.

## 3. Projection

No C++, conforme a tecla P/O:
- **Perspectiva**: `Matrix_Perspective(π/3, aspect, −0.1, −10)` retorna `−M·P`. A matriz `P` coloca `z` em `w` (a última linha é `0 0 1 0`), e `M` é a ortográfica que leva o volume de visão para o cubo `[−1,1]³`.
- **Ortográfica**: `Matrix_Orthographic(l, r, b, t, n, f)`, com `t` proporcional à distância da câmera para simular zoom.

A matriz é aplicada no vertex shader, na mesma linha do `gl_Position`. O resultado são as **coordenadas de recorte (clip coordinates)**, ainda **antes** da divisão por `w`.

## 4. Clipping

Nenhuma linha de código faz o clipping. A GPU faz isso automaticamente com o `gl_Position`: descarta, ou recorta, tudo que estiver fora de
```
−w ≤ x ≤ w,   −w ≤ y ≤ w,   −w ≤ z ≤ w
```
O código controla o clipping de forma **indireta**:
- `nearplane`/`farplane` e o FOV definem o frustum. Algo mais perto que 0.1 ou mais longe que 10 unidades some.
- O `−M·P` existe justamente para esse teste funcionar, porque ele só vale com `w > 0` (o comentário em [matrices.h:301-320](include/matrices.h#L301-L320) explica).

Logo depois, a GPU faz a **divisão perspectiva** (`x/w, y/w, z/w`) e chega às **NDC**.

## 5. Screen Mapping

A GPU leva as NDC `[−1,1]` para pixels da janela com a transformação de **viewport**, que o código configura:
```cpp
void FramebufferSizeCallback(GLFWwindow* window, int width, int height) {
    glViewport(0, 0, width, height);
    g_ScreenRatio = (float)width / height;
}
```
Essa função é chamada na inicialização e sempre que a janela muda de tamanho. O `z` das NDC também é mapeado, para `[0,1]`, e esse valor é o que vai para o Z-buffer.

## 6. Fragment Generation (rasterização)

Começa com `glDrawElements(...)` dentro de `DrawVirtualObject()` ([main.cpp:545](src/main.cpp#L545)). A GPU monta os triângulos a partir dos índices e:

1. **Descarta triângulos de costas (backface culling)**, que o código liga em [main.cpp:331-333](src/main.cpp#L331-L333):
   ```cpp
   glEnable(GL_CULL_FACE); glCullFace(GL_BACK); glFrontFace(GL_CCW);
   ```
   Um triângulo cujos vértices aparecem em sentido horário na tela está de costas e nem gera fragmentos.
2. **Descobre quais pixels cada triângulo cobre**: cada um vira um fragmento.
3. **Interpola os atributos**: cada variável `out` do vertex shader (`position_world`, `position_model`, `normal`, `texcoords`) é interpolada entre os 3 vértices, com correção de perspectiva, e chega como `in` no fragment shader.

Esse passo 3 é a ligação entre os dois shaders, e o comentário no topo do [shader_vertex.glsl:14-17](src/shader_vertex.glsl#L14-L17) chama atenção para ele.

## 7. Fragment Shading

[shader_fragment.glsl](src/shader_fragment.glsl) roda **uma vez por fragmento** e calcula a cor:

1. **Posição da câmera**: `inverse(view) * (0,0,0,1)`.
2. **Coordenadas de textura** conforme `object_id`: projeção esférica (esfera), planar XY com a AABB (coelho) ou `texcoords` do `.obj` (plano).
3. **Amostragem**: `Kd0 = texture(TextureImageN, vec2(U,V)).rgb`.
4. **Iluminação de Lambert** com um termo ambiente: `color = Kd0 * (max(0, n·l) + 0.01)`.
5. **Correção gamma**: `pow(color, 1/2.2)`.

A saída é `out vec4 color`.

## 8. Visibility (Z-buffer)

Também é fixa na GPU. O código só liga e limpa:
```cpp
glEnable(GL_DEPTH_TEST);                               // main.cpp:328, uma vez
glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT);    // main.cpp:350, todo quadro
```
Para cada fragmento, a GPU compara a profundidade dele com a que já está no Z-buffer naquele pixel. Se ele estiver mais perto, a cor vai para o framebuffer e o Z-buffer é atualizado. Se não, ele é descartado. Por isso a **ordem dos `DrawVirtualObject` não importa** para objetos opacos: o coelho atrás da esfera fica escondido mesmo que seja desenhado depois.

O `glClear` do depth buffer em todo quadro é essencial. Sem ele, as profundidades do quadro anterior continuariam no buffer e bloqueariam o novo desenho.

No fim, `glfwSwapBuffers()` mostra o framebuffer pronto na tela.

**Resumo do fluxo de um vértice até o pixel:**

```
model_coefficients (modelo)
  ─ model ─────────▶ mundo                    ┐
  ─ view ──────────▶ câmera                   │ vertex shader
  ─ projection ────▶ clip coords (gl_Position)┘
  ─ clipping ──────▶ descarta o que está fora do frustum      ┐
  ─ ÷ w ───────────▶ NDC [−1,1]³                              │
  ─ glViewport ────▶ pixels da janela + z ∈ [0,1]             │ GPU (fixo)
  ─ culling + rasterização + interpolação ─▶ fragmentos       ┘
  ─ fragment shader ─▶ cor (textura + Lambert + gamma)          programável
  ─ depth test ────▶ framebuffer                                GPU (fixo)
```

Qual tipo de shading esse projeto usa?

----- CLAUDE [2026-11-01 14:11:29] -----
O projeto usa **Phong shading**, com um detalhe: o modelo de iluminação dele ainda é **só Lambert**, não o Phong completo. São duas coisas diferentes, e as aulas 17/18 também separam as duas.

## Interpolação de shading: Phong

Existem três formas clássicas de decidir **onde** a iluminação é calculada:

| Tipo | Onde a iluminação é calculada | O que é interpolado |
|---|---|---|
| Flat | uma vez por triângulo | nada (o triângulo inteiro tem uma cor só) |
| Gouraud | em cada **vértice** (vertex shader) | a **cor** |
| **Phong** | em cada **fragmento** (fragment shader) | a **normal** |

O projeto é Phong porque:
- o vertex shader **não calcula cor nenhuma**, só passa a normal adiante: `normal = inverse(transpose(model)) * normal_coefficients;`
- o rasterizador interpola essa normal entre os vértices;
- o fragment shader normaliza de novo a normal interpolada (`n = normalize(normal)`) e calcula a iluminação **por pixel**.

Um ponto que costuma confundir: `ComputeNormals()` tem um comentário falando em *"método proposto por Gouraud"*. Isso se refere só a **como calcular a normal de cada vértice**, pela média das normais das faces vizinhas. **Não** é Gouraud shading. Tanto o Gouraud quanto o Phong shading precisam dessas normais por vértice. O que muda entre eles é se a interpolação acontece **antes** ou **depois** de calcular a iluminação.

## Modelo de iluminação: Lambert + ambiente

A equação que o fragment shader calcula é:

```glsl
color.rgb = Kd0 * (max(0, dot(n, l)) + 0.01);
```

Comparando com a equação de Phong dos slides:

$$
\text{cor}_p = \underbrace{k_d\, I \max(0, n\cdot l)}_{\text{difuso (Lambert)}} + \underbrace{k_a I_a}_{\text{ambiente}} + \underbrace{k_s\, I \max(0, r\cdot v)^q}_{\text{especular}}
$$

- **Difuso**: ✅ implementado, com `Kd` vindo da textura e `I = 1`.
- **Ambiente**: ✅ simplificado. É o `+ 0.01`, multiplicado por `Kd0`, ou seja, `ka = Kd` e `Ia = 0.01`.
- **Especular**: ❌ não implementado. O shader já calcula `v` (o vetor até a câmera), mas não usa.

## Por que importa para o trabalho

Com só o termo difuso, Gouraud e Phong shading ficam quase iguais visualmente. A diferença aparece com o **termo especular**: no Gouraud o brilho fica borrado ou some nos triângulos grandes, e no Phong ele fica nítido. Se o enunciado pedir os dois tipos de shading e os dois modelos de iluminação (o do INF01047 costuma pedir), vocês precisam:
1. adicionar o termo especular (Phong ou Blinn-Phong) no fragment shader;
2. ter pelo menos um objeto com **Gouraud shading**, ou seja, iluminação calculada no vertex shader e cor interpolada.

Como tu faria pra fazer um terreno infinito?

----- CLAUDE [2026-11-01 14:41:00] -----
Eu faria um **terreno procedural em pedaços (chunks)** que vão sendo reciclados conforme o pássaro avança. Na prática, o terreno nunca existe inteiro na memória. Existem só alguns pedaços em volta do jogador, e todos são gerados pela mesma função matemática.

## 1. A base: uma função de altura `h(x, z)`

O mais importante é definir o terreno como uma **função** em vez de um modelo `.obj`:

```cpp
float TerrainHeight(float x, float z);  // retorna a altura y do chão em (x,z)
```

Essa função fica como única fonte de verdade para tudo:
- **renderização**: os vértices de cada chunk são `(x, h(x,z), z)`;
- **física**: o pássaro está no chão se `passaro.y <= h(passaro.x, passaro.z)`;
- **inclinação da rampa**: a derivada de `h`, que define se ele é lançado ou ganha velocidade na descida.

Como `h` é determinística (o mesmo `x` dá sempre a mesma altura), dá para gerar qualquer trecho do terreno a qualquer momento, e ele "continua" sem emendas.

### Como fazer os morros no estilo Tiny Wings

Eu usaria **pontos de controle com altura pseudoaleatória, ligados por uma curva cúbica suave**:

```cpp
// Altura "aleatória" mas determinística para o ponto de controle i
float ControlHeight(int i) {
    unsigned int h = i * 374761393u;
    h = (h ^ (h >> 13)) * 1274126177u;
    return (h & 0xFFFF) / 65535.0f * AMPLITUDE;
}

float TerrainHeight(float x, float z) {
    float s = x / SPACING;               // espaçamento entre os topos dos morros
    int   i = (int)floor(s);
    float t = s - i;                     // posição local em [0,1)
    // Hermite com tangentes nulas → morros e vales suaves, como em Tiny Wings
    float t2 = t*t*(3 - 2*t);
    return mix(ControlHeight(i), ControlHeight(i+1), t2);
}
```

Isso cai direto na **Aula 16 (Curvas e Superfícies)**. Dá para trocar a interpolação por uma **Bézier cúbica** ou uma **Catmull-Rom** e escolher o formato das rampas, o que provavelmente ajuda a cumprir algum requisito do enunciado sobre curvas. Para variar a pista na direção `z`, basta somar um termo leve, como `0.3*sin(z*0.5)`.

## 2. Chunks reciclados (o "infinito")

Como o jogo avança quase sempre numa direção só, como em Haste, uma fila de chunks basta:

```
    [chunk 0][chunk 1][chunk 2][chunk 3][chunk 4]  →  direção do pássaro
        ↑ pássaro aqui
```

- Cada chunk é uma **grade de N×M vértices** (por exemplo 64×32) cobrindo um trecho de, digamos, 20 unidades.
- Na inicialização, você cria `K` chunks (por exemplo 6), cada um com seu VAO/VBO, reaproveitando o código de `BuildTrianglesAndAddToVirtualScene`.
- Todo quadro: quando o pássaro **passa** do chunk mais antigo, esse chunk vai para a frente da fila. Os vértices dele são recalculados para a nova posição e reenviados com `glBufferSubData`. Os índices não mudam, porque a topologia da grade é sempre a mesma.

Assim não há alocação nova durante o jogo, só uma atualização de VBO a cada poucos segundos. Isso é bem leve.

## 3. Normais sem `ComputeNormals`

Como `h` é uma função, a normal sai direto das derivadas (diferenças finitas):

```cpp
const float e = 0.01f;
float dhdx = (TerrainHeight(x+e, z) - TerrainHeight(x-e, z)) / (2*e);
float dhdz = (TerrainHeight(x, z+e) - TerrainHeight(x, z-e)) / (2*e);
glm::vec4 n = normalize(glm::vec4(-dhdx, 1.0f, -dhdz, 0.0f));
```

Esse mesmo `dhdx` dá a **inclinação** que a física do pássaro precisa.

## 4. Textura que não "emenda"

Calcule as coordenadas de textura a partir da **posição no mundo**, não do índice do chunk:

```glsl
U = position_world.x * 0.2;
V = position_world.z * 0.2;
```

Isso exige `GL_REPEAT` no sampler, que hoje está `CLAMP_TO_EDGE` em `LoadTextureImage`. Com isso, a textura passa de um chunk para o outro sem costura.

## 5. Esconder o fim do mundo

Os chunks acabam em algum lugar, e o `farplane = -10` atual corta tudo muito perto. Duas medidas:
- aumentar o `farplane` para algo como `-200`, e gerar chunks até um pouco antes disso;
- adicionar **neblina** no fragment shader, misturando a cor com a cor do céu conforme a distância:
  ```glsl
  float d = length(camera_position - p);
  color.rgb = mix(color.rgb, cor_do_ceu, smoothstep(80.0, 180.0, d));
  ```
  Isso também combina com o pôr do sol, já que `cor_do_ceu` pode vir do mesmo uniform `hora_do_dia`.

## Alternativa mais simples (se faltar tempo)

Uma **grade única que acompanha o pássaro**: a malha é fixa e plana, e o **vertex shader** calcula `y = h(x,z)` a partir da posição no mundo. O infinito sai de graça, sem gerenciar chunks. A desvantagem é que `h` precisa existir duplicada em C++ (para a física) e em GLSL (para o desenho), e as duas versões têm que bater exatamente. Além disso, a grade precisa andar em passos do tamanho da célula, senão o terreno parece "ondular". Por isso eu prefiro os chunks.

----- CLAUDE [2026-11-01 14:43:43] -----
A ideia é tratar o **perfil do terreno** (a altura `y` ao longo de `x`, a direção em que o pássaro corre) como uma sequência de **curvas de Bézier cúbicas emendadas**. Cada curva liga o topo de um morro ao fundo do vale seguinte, depois do vale ao próximo topo, e assim por diante.

## Um segmento: do topo ao vale

Uma Bézier cúbica tem 4 pontos de controle e é definida por:

$$
B(t) = (1-t)^3 P_0 + 3t(1-t)^2 P_1 + 3t^2(1-t) P_2 + t^3 P_3,\quad t\in[0,1]
$$

Para um trecho do terreno:

```
 y
 │  P0●────●P1                       P0 = topo do morro
 │      ‾‾‾‾‾╲                       P3 = fundo do vale
 │             ╲                     P1 = ao lado de P0, mesma altura
 │               ╲___                P2 = ao lado de P3, mesma altura
 │            P2●────●P3
 └──────────────────────────── x
```

- **P0 e P3** são os pontos por onde a curva **passa**: o topo e o vale.
- **P1 e P2** não ficam na curva. Eles **puxam** a curva e definem as tangentes. Com P1 na mesma altura de P0, a curva sai do topo **na horizontal**. Com P2 na mesma altura de P3, ela chega ao vale também na horizontal. O resultado é um morro arredondado, sem bico.

## Como ter a altura num `x` qualquer

Aqui tem uma pegadinha. A Bézier dá `x` **e** `y` em função de `t`, mas a física precisa do contrário: "o pássaro está em `x = 37.2`, qual é a altura do chão?"

O truque é espaçar os pontos de controle **igualmente em x**:

```
P0.x = x0,  P1.x = x0 + Δ/3,  P2.x = x0 + 2Δ/3,  P3.x = x0 + Δ
```

Com esse espaçamento, `x(t)` fica **linear** em `t`, e então `t = (x − x0) / Δ` sai direto. Só o `y` é curvo:

```cpp
float BezierTerrainHeight(float x)
{
    int   i  = (int)floor(x / SPACING);           // qual segmento
    float t  = x / SPACING - i;                   // posição dentro dele, em [0,1)

    float y0 = ControlHeight(i);                  // P0.y (pseudoaleatório)
    float y3 = ControlHeight(i + 1);              // P3.y
    float y1 = y0;                                // P1.y = P0.y → tangente horizontal
    float y2 = y3;                                // P2.y = P3.y → tangente horizontal

    float s = 1.0f - t;
    return s*s*s*y0 + 3*t*s*s*y1 + 3*t*t*s*y2 + t*t*t*y3;
}
```

## O código que mostrei antes já era isso

Com `y1 = y0` e `y2 = y3`, a Bézier se simplifica:

$$
y(t) = y_0\,\underbrace{(1 - 3t^2 + 2t^3)}_{} + y_3\,(3t^2 - 2t^3)
$$

Essa é exatamente a interpolação `mix(y0, y3, t*t*(3-2*t))` da resposta anterior. Ou seja, aquele `smoothstep` **é** uma Bézier cúbica com tangentes horizontais. A diferença é que, escrevendo na forma de Bézier, vocês controlam o formato.

## O que a Bézier dá a mais

Mexendo em P1 e P2, vocês controlam a **forma de cada rampa**:

- **Descida longa e subida curta e íngreme**, que vira uma rampa de lançamento: coloque P2 mais perto de P3 e P1 mais longe de P0. A curva desce devagar e "dobra" no fim.
- **Topos achatados** (platôs): P1 e P2 bem próximos das pontas.
- **Variedade**: sorteie (de forma determinística) a posição de P1 e P2 para cada segmento, e cada morro fica diferente.

Para não ter "quinas" nas emendas entre segmentos, o P2 de um segmento, o ponto de junção P3 e o P1 do próximo segmento precisam ficar **na mesma reta** (continuidade da tangente, G¹/C¹, da Aula 16). Com tangentes horizontais isso já acontece automaticamente: os três pontos têm a mesma altura.

## Ligando com o resto

- A derivada da Bézier dá a **inclinação** em cada ponto, exatamente o que a mecânica de momentum precisa:
  $$B'(t) = 3(1-t)^2(P_1-P_0) + 6t(1-t)(P_2-P_1) + 3t^2(P_3-P_2)$$
- A **malha** do chunk continua sendo uma grade. Cada vértice só pergunta `BezierTerrainHeight(x)` para saber a altura.
- No relatório, vocês podem dizer que o terreno é uma **superfície gerada pela extrusão, ao longo de `z`, de uma curva de Bézier cúbica por partes**. Isso deixa explícito o uso do conceito da aula.

A volta é **contínua**: a velocidade desce suavemente até a base, sem salto. Tecnicamente ela muda em degraus, um por quadro, mas os degraus são tão pequenos que você não percebe.

## O que acontece quando você solta o botão

Sem dive, a inclinação do terreno é **ignorada**, então tanto faz estar descendo. A cada quadro o código faz:

```cpp
g_PlayerSpeed += (PLAYER_BASE_SPEED - g_PlayerSpeed) * std::min(1.0f, PLAYER_RETURN_RATE * delta_t);
```

Ou seja, a cada quadro a velocidade anda **uma fração fixa da distância que falta** até a base. Com `PLAYER_RETURN_RATE = 3` e 144 fps, essa fração é `3 × (1/144) ≈ 2,1%`. Isso é um **decaimento exponencial**:

$$
v(t) \approx 5 + (v_0 - 5)\, e^{-3t}
$$

Exemplo: soltando o botão a 10 de velocidade.

| Tempo depois de soltar | Velocidade | Excesso que sobra |
|---|---|---|
| 0 s | 10,00 | 100% |
| 0,25 s | 7,36 | 47% |
| 0,5 s | 6,12 | 22% |
| 1 s | 5,25 | 5% |
| 1,5 s | 5,06 | 1% |

A queda é **rápida no começo e cada vez mais lenta**, porque quanto mais perto da base, menor a diferença, e menor o passo. Na matemática ela nunca chega exatamente a 5. Na prática, em uns 2 segundos fica indistinguível.

## Contínuo ou discreto?

- **Na tela:** contínuo. São 144 passos por segundo, cada um mudando a velocidade em no máximo 2% do que falta. Não há tranco.
- **No código:** discreto. É uma aproximação de Euler da exponencial acima, com um passo por quadro. Como o passo depende de `delta_t`, o resultado é praticamente o mesmo a 30 ou a 144 fps. O `min(1, ...)` protege contra quadros muito lentos: sem ele, um quadro de mais de 1/3 s "passaria do ponto" e a velocidade ficaria abaixo da base.

A outra opção era fazer `g_PlayerSpeed = PLAYER_BASE_SPEED` direto ao soltar. Aí sim seria **discreto**: de 10 para 5 em um único quadro, um tranco visível.

## Curiosidade: e se você **segurar** o dive numa descida contínua?

A velocidade também não cresce para sempre. Ela tende a uma **velocidade terminal**, quando a gravidade empata com o arrasto:

$$
G\, n_x = 0{,}15\,(v - 5) \;\Rightarrow\; v_{\text{terminal}} = 5 + \frac{G\, n_x}{0{,}15}
$$

Numa rampa de 45° (`n_x ≈ 0,71`), isso dá cerca de **51**. Nos morros atuais você nunca chega perto disso, porque as descidas são curtas: o máximo na simulação foi 10,5. Se vocês fizerem descidas longas, esse é o teto.

Dá para fazer sem mexer no terreno. A ideia é o jogador ter **dois estados**, *no chão* e *no ar*, e trocar entre eles por uma regra física simples.

## 1. Estado do jogador

Hoje o jogador só tem `x` e uma velocidade ao longo do chão. No ar ele precisa de uma posição e de uma velocidade em 2D:

```cpp
float g_PlayerX, g_PlayerY;     // posição (y deixa de ser sempre TerrainHeight)
float g_PlayerVX, g_PlayerVY;   // velocidade
bool  g_PlayerOnGround;
```

No chão, o vetor velocidade é a velocidade escalar de hoje vezes a **tangente** do terreno:

$$\vec v = v\,\vec t = v\,\frac{(1,\; h'(x))}{\sqrt{1+h'^2}}$$

## 2. Decolagem: quando o chão "foge" da bola

A bola sai do chão quando, **sem nada a segurando, ela ficaria acima do terreno**. No topo de um morro, o chão curva para baixo. Se a bola estiver rápida, ela continuaria reto (seguindo a trajetória balística) e o chão sumiria embaixo dela.

O teste prático, a cada quadro no chão:

```cpp
// Onde a bola estaria no próximo quadro se estivesse livre (só gravidade)
float next_x = x + vx*dt;
float next_y = y + vy*dt - 0.5f*G*dt*dt;

if (next_y > TerrainHeight(next_x, 0))   // o chão curvou para baixo mais rápido que a queda
    g_PlayerOnGround = false;             // decolou, mantendo vx e vy
```

Esse é o critério físico de verdade: a bola descola quando a aceleração centrípeta que ela precisaria para acompanhar a curva (`v²·κ`, onde κ é a curvatura) passa da gravidade. Com os morros atuais, a curvatura no topo é cerca de `6Δh/L² ≈ 0,4`. Então a bola decola em topos com velocidade acima de mais ou menos `√(G/κ) ≈ 5`. Sem dive ela raspa no limite, e com o embalo do dive (10) ela voa de verdade. **Quem desce bem é lançado mais longe**, sem nenhuma regra especial no código.

## 3. No ar: planar ou mergulhar

No ar a gravidade **precisa** agir sempre, senão a bola não volta. O dive passa a controlar **quanto**:

```cpp
float g = diving ? G * DIVE_MULT    // mergulho: cai rápido, para pousar na descida
                 : G * GLIDE_MULT;  // planando: cai devagar, voo longo
vy -= g * dt;
vy  = std::max(vy, -MAX_GLIDE_FALL);   // sem dive: limita a velocidade de queda (paraquedas)
x  += vx * dt;
y  += vy * dt;
```

Valores para começar: `GLIDE_MULT ≈ 0.35`, `DIVE_MULT ≈ 2.5`, `MAX_GLIDE_FALL ≈ 4`. Planar significa principalmente **cair devagar mantendo `vx`**. Se quiserem algo mais elaborado, dá para converter um pouco de `vx` em sustentação, mas isso não é necessário para o efeito.

## 4. Pouso: alinhamento conta

Quando `y <= TerrainHeight(x)`, a bola pousou. A velocidade se divide em duas partes: a **ao longo** do terreno (que fica) e a **contra** o terreno (que o chão absorve):

```cpp
float v_along = vx*t.x + vy*t.y;   // projeção na tangente
y = TerrainHeight(x, 0);
g_PlayerSpeed = std::max(v_along, PLAYER_MIN_SPEED);
g_PlayerOnGround = true;
```

Isso dá exatamente a mecânica do SPEC, *"pousar alinhado com as rampas e manter velocidade"*:
- **Pousar numa descida**, com a trajetória paralela ao chão: quase toda a velocidade é mantida.
- **Pousar numa subida**, ou de cara no chão: a projeção é pequena e a velocidade cai muito.

Por isso o dive no ar é útil: ele serve para "mirar" a descida do próximo morro.

- **Câmera:** ela olha para `(x, y)` do jogador, e isso já funciona. Talvez valha suavizar o `y` dela, para não sacudir no pouso.

- **Terreno:** se a decolagem ficar tímida, dá para aumentar a altura dos morros ou encurtar os segmentos. Mais curvatura no topo significa decolar com menos velocidade.

- **`i` par**: topo de morro, altura sorteada entre 2 e 4;
- **`i` ímpar**: fundo de vale, altura sorteada entre −1 e 0,5.

O "sorteio" é uma função hash do próprio `i`. O mesmo `i` sempre dá a mesma altura, então qualquer pedaço do terreno pode ser recalculado a qualquer momento e sempre sai igual. É isso que permite o terreno infinito.

```
 y
 4 ┤   ●               ●                    ● = ponto de controle i
   │                         ●                 (topos e vales alternados)
 2 ┤         
 0 ┤         ●     
-1 ┤                     ●         ●
   └───┬─────┬─────┬─────┬─────┬─────┬──▶ x
       0     8    16    24    32    40
      i=0   i=1   i=2   i=3   i=4   i=5
```

## 2. Um segmento = uma Bézier cúbica

Entre dois pontos vizinhos `i` e `i+1` há uma Bézier cúbica com 4 pontos de controle ([terrain.cpp:78](src/terrain.cpp#L78)):

```
P0 = (x_i,        y_i)       ← começa no ponto i
P1 = (x_i + L/3,  y_i)       ← mesma altura de P0
P2 = (x_i + 2L/3, y_{i+1})   ← mesma altura de P3
P3 = (x_i + L,    y_{i+1})   ← termina no ponto i+1
```

```
 P0 ●━━━━━━━━● P1
     ‾‾‾‾‾╲              A curva passa por P0 e P3.
            ╲            P1 e P2 só "puxam" a curva: como estão na
             ╲___        mesma altura das pontas, ela sai e chega
       P2 ●━━━━━━━━● P3  na horizontal → morros arredondados.
```

## 3. Como calcular a altura num `x` qualquer

Uma Bézier dá `(x, y)` em função de um parâmetro `t ∈ [0,1]`. Mas o jogo pergunta o contrário: *"em `x = 37,2`, qual a altura?"*.

O truque é que P0, P1, P2 e P3 estão **igualmente espaçados em x** (a 0, L/3, 2L/3 e L). Com isso, a parte `x(t)` da Bézier vira uma reta, e `t` sai direto de `x`:

```cpp
float s = x / TERRAIN_SEGMENT_LENGTH;   // 37,2 / 8 = 4,65
int   i = (int)floorf(s);               // segmento 4
t = s - i;                              // t = 0,65 dentro dele
```

Depois, `TerrainHeight` ([terrain.cpp:91](src/terrain.cpp#L91)) aplica a fórmula da Bézier (polinômios de Bernstein) só no `y`:

$$
y(t) = (1-t)^3\,y_0 + 3t(1-t)^2\,y_1 + 3t^2(1-t)\,y_2 + t^3\,y_3
$$

```cpp
float s = 1.0f - t;
return s*s*s*y0 + 3.0f*t*s*s*y1 + 3.0f*t*t*s*y2 + t*t*t*y3;
```

## 4. A inclinação: derivada da Bézier

`TerrainSlope` ([terrain.cpp:102](src/terrain.cpp#L102)) usa a derivada da Bézier, que é uma Bézier quadrática dos vetores entre os pontos de controle:

$$
\frac{dy}{dt} = 3(1-t)^2(y_1-y_0) + 6t(1-t)(y_2-y_1) + 3t^2(y_3-y_2)
$$

Como queremos `dy/dx`, e não `dy/dt`, entra a regra da cadeia: `t = x/L` dá `dt/dx = 1/L`, então `dy/dx = (dy/dt) / L`.

Essa inclinação é usada em três lugares: na **normal** da iluminação, na **gravidade** do dive (`G · n.x`) e nos testes de **decolagem e pouso**.

## 5. Por que não há quinas nas emendas

Na Aula 16, duas Béziers emendam de forma suave quando:

- **C⁰ (posição):** o fim de uma é o começo da outra. Aqui, o `P3` do segmento `i` e o `P0` do segmento `i+1` são o mesmo ponto `(x_{i+1}, y_{i+1})`.
- **C¹ (tangente):** `P2`, o ponto de junção e o `P1` do próximo segmento ficam na mesma reta. Aqui os três têm a mesma altura `y_{i+1}`, ou seja, estão numa reta horizontal.

Isso foi conferido numericamente: o salto de altura nas emendas é ~0,0000002 (erro de arredondamento) e a inclinação é contínua.

## 6. Da curva para a superfície 3D

A superfície é a **extrusão** do perfil em `z`: `h(x, z) = y(x)`, a mesma curva repetida em toda a largura da pista. `FillChunk` ([terrain.cpp:117](src/terrain.cpp#L117)) amostra essa função numa grade de 65 × 21 vértices por chunk:

```cpp
float y = TerrainHeight(x, z);                // posição do vértice
float dhdx = TerrainSlope(x, z);              // normal = (-dh/dx, 1, 0) normalizada
texture_coefficients.push_back(x * 0.25f);    // textura pela posição no mundo
```

Cada quadrado da grade vira 2 triângulos, e o resultado é uma malha comum, desenhada com `glDrawElements` como os `.obj`.

## Uma observação honesta, para o relatório

Com `y1 = y0` e `y2 = y3`, essa Bézier se simplifica para
$$y(t) = y_0 + (y_3 - y_0)\,(3t^2 - 2t^3)$$
que é a curva de Hermite com tangentes nulas (o `smoothstep`). Ou seja, hoje os pontos internos P1 e P2 não dão nenhuma liberdade extra: estão "travados" para garantir a tangente horizontal.

Para o uso de Bézier ficar mais evidente e útil, dá para soltá-los. Por exemplo, deslocar P1 e P2 em `x` gera rampas assimétricas (descida longa e subida curta, ótima para lançamento). A condição de C¹ continua sendo manter P2, a junção e o P1 seguinte alinhados. Mas se o espaçamento em `x` deixar de ser igual, `x(t)` deixa de ser linear, e achar `t` a partir de `x` passa a exigir uma busca numérica.

O arrasto é uma "força" que vai tirando aos poucos a velocidade que passa do piso de 5. Fica em [main.cpp](src/main.cpp), em `UpdatePlayerOnGround`:

```cpp
float drag_acceleration = -PLAYER_DRAG * (g_PlayerSpeed - PLAYER_MIN_SPEED);
```

## O que ele faz

A desaceleração é proporcional ao **excesso** de velocidade, com `PLAYER_DRAG = 0.15`:

| Velocidade | Excesso | Desaceleração do arrasto |
|---|---|---|
| 5 | 0 | 0, ou seja, no piso ele não age |
| 7 | 2 | 0,3 u/s² |
| 10 | 5 | 0,75 u/s² |
| 15 | 10 | 1,5 u/s² |

Num trecho plano, sem gravidade agindo, o excesso cai pela metade a cada **~4,6 s** (decaimento exponencial). Exemplo: chegou no plano a 15, depois de 4,6 s está a 10, e depois de mais 4,6 s está a 7,5.

Comparado com a gravidade ele é fraco: numa rampa de 30°, a gravidade dá 4,9 u/s². Por isso o arrasto quase não aparece dentro de uma descida. Ele age ao longo do tempo, gastando aos poucos o embalo acumulado.

## Por que ele existe

O motivo é o **piso**. Sem arrasto, o piso cria energia do nada:

1. Na **descida**, a gravidade acelera a bola, por exemplo de 5 para 9.
2. Na **subida**, a gravidade deveria frear de volta, e em algum ponto a bola ficaria abaixo de 5. Mas o piso segura a velocidade em 5. A bola chega no topo sem ter "pago" a subida inteira.
3. Na **próxima descida**, ela ganha velocidade de novo.

Com física real, subir e descer um morro da mesma altura devolveria a mesma velocidade. Com o piso, cada morro deixa um pouquinho de lucro, e sem nada para compensar a velocidade cresceria sem limite ao longo do jogo. O arrasto é o "imposto" que equilibra esse lucro: quanto mais rápido, mais ele tira. Na simulação, a velocidade fica entre 5 e ~14 em vez de explodir.

## Observação

Não é arrasto do ar de verdade. O do ar real cresce com v² e puxa em direção a 0, não a 5. Este é uma simplificação de jogabilidade, feita para empurrar a velocidade de volta ao piso.

Se quiser ajustar:
- **0.15 → 0.05:** o embalo dura bem mais (meia-vida de ~14 s), e a velocidade máxima sobe.
- **0.15 → 0.3:** o embalo some mais rápido (~2,3 s), e o jogo fica mais "controlado".

## 1. Linha base constante

O terreno passaria a oscilar em torno de y = 0, com vales abaixo e cristas acima, sem tendência de subir ou descer. Para não ficar regular, cada nó da curva teria:
- **altura sorteada:** vales de −2 a −0,5 e cristas de 1 a 4;
- **posição em x com deslocamento sorteado:** `x_i = i·L + jitter(i)`, o que deixa os espaçamentos desiguais e ainda permite achar o segmento com uma fórmula fechada.

A variação em z continuaria, mas mais suave.

## 2. Rampas assimétricas para ganhar altura

Esta é a parte principal. Cada trecho vale → crista passaria a ser uma **rampa**: no lugar de `P2.y = P3.y`, `P2` fica abaixo da crista. Assim a curva chega no topo ainda subindo, como a borda de um trampolim, e depois cai do outro lado.

```
        lábio
         /\
        /  \____
  _____/        \___   ← antes: topo achatado, decola na horizontal
```

A altura que a bola ganha acima do lábio é:

**h = (v · sen θ)² / (2g)**

onde v é a velocidade no lábio e θ é o ângulo de saída. Planando (g ≈ 6,4):

| v no lábio | θ = 0° (hoje) | θ = 25° | θ = 35° |
|---|---|---|---|
| 10 | ~0 | 1,4 | 2,6 |
| 15 | ~0 | 3,2 | 5,8 |
| 20 | ~0 | 5,6 | 10,3 |

O lábio fica com uma quina, ou seja, contínuo mas sem tangente contínua (C0). É intencional, porque é o que faz uma rampa funcionar. A física atual já trata isso: no lábio o terreno "some" debaixo da bola, o teste de decolagem dispara, e ela sai com a velocidade apontando para cima. Os vales continuam suaves, já que uma quina côncava daria um tranco.

O jogo vira um ritmo: **dive na descida, para ganhar velocidade no vale**, e depois **soltar na rampa**, para não frear com a gravidade amplificada. Isso faz a bola sair alta do lábio.

| | `PLAYER_GLIDE_GRAVITY_MULT` (0.4) | `PLAYER_GLIDE_MAX_FALL` (4.0) |
|---|---|---|
| **O que é** | Fração da gravidade que age ao planar | Velocidade máxima de queda ao planar |
| **Unidade** | Multiplica a aceleração: 0,4 × 16 = 6,4 u/s² | Velocidade: 4 u/s |
| **Controla** | **Quão rápido** a velocidade de queda aumenta | **Até onde** a velocidade de queda pode chegar |
| **Analogia** | O peso do paraquedista | A velocidade terminal com o paraquedas aberto |

## Na prática

Quando a bola sai do chão, a velocidade vertical `VY` vai diminuindo, ou seja, ela passa a cair cada vez mais rápido. Isso acontece em duas fases:

1. **Acelerando:** `VY` diminui 6,4 por segundo (menos a sustentação, que age só na descida). A trajetória é uma parábola.
2. **No limite:** quando `VY` chega a −4, o código trava ali:
   ```cpp
   g_PlayerVY = std::max(g_PlayerVY, -PLAYER_GLIDE_MAX_FALL);
   ```
   A partir desse ponto a bola cai a velocidade **constante** e a trajetória vira uma linha reta inclinada. É a fase que dá a sensação de "planar". O multiplicador de gravidade deixa de importar.

Quanto tempo leva até chegar no limite depende da velocidade horizontal, por causa da sustentação:
- **devagar** (gravidade efetiva ~6,4): cerca de **0,6 s**;
- **rápido** (sustentação máxima, gravidade efetiva ~1,3): cerca de **3 s**.

## O que muda ao mexer em cada uma

- **Aumentar o `GLIDE_GRAVITY_MULT`:** a bola começa a cair mais cedo e o topo da parábola fica mais baixo, mas a velocidade final de queda é a mesma.
- **Aumentar o `GLIDE_MAX_FALL`:** a queda inicial é igual, mas a bola continua acelerando por mais tempo antes de estabilizar, então a descida final fica mais íngreme.

As duas só valem **sem dive**. Com dive, a gravidade é 16 × 1,5 = 24 e não há limite de velocidade de queda.

|---|---|---|---|

A queda da bola eh exponencial?

----- CLAUDE [2026-11-01 20:25:03] -----
Não. A queda é **parabólica**: a aceleração é constante, então a velocidade cresce de forma linear e a altura cai com o quadrado do tempo.

## Por que é parabólica

No ar, a cada passo o código faz ([main.cpp](src/main.cpp), `UpdatePlayerInAir`):

```cpp
g_PlayerY  += g_PlayerVY * delta_t - 0.5f * g * delta_t * delta_t;
g_PlayerVY -= g * delta_t;
```

Com `g` constante, isso é o movimento uniformemente variado:

- **velocidade:** `VY(t) = VY₀ − g·t`, linear;
- **altura:** `Y(t) = Y₀ + VY₀·t − ½·g·t²`, quadrática.

E `g` é constante durante a queda porque:
- **com dive,** vale sempre 24;
- **planando,** vale `8 − sustentação`, e a sustentação depende só de `VH`, que não muda no ar. Ela muda uma vez, no topo do voo, quando `VY` passa a ser negativa e a sustentação entra. Na prática são duas parábolas emendadas: uma subindo, outra descendo mais devagar.

## Quando ela deixa de ser parábola

Com o **limite de queda** (`PLAYER_GLIDE_MAX_FALL`), quando `VY` chega no limite a velocidade trava e a altura passa a cair **linearmente**. Você deixou o limite em 99, então isso quase nunca acontece.

## Onde existe algo exponencial

Seria exponencial se houvesse uma resistência proporcional à velocidade. Aí a velocidade de queda se aproximaria de um limite, a velocidade terminal, sem nunca chegar a ele exatamente. No ar não fizemos isso.

O único comportamento exponencial do jogo está **no chão**: o arrasto `−PLAYER_DRAG · (v − v_min)` faz o excesso de velocidade cair exponencialmente em direção ao piso. Com o seu arrasto de 0.01, a meia-vida é de cerca de 70 s, então quase não se percebe.

Agora me explique como funcinoa a geracao de terreno atualmente

----- CLAUDE [2026-11-01 20:30:26] -----
A geração do terreno, que fica toda em [terrain.cpp](src/terrain.cpp), se divide em duas partes:
1. **Uma função matemática** `h(x, z)` que dá a altura de qualquer ponto do mundo. A física usa essa mesma função.
2. **Uma malha de triângulos** montada a partir dela, só no trecho perto da bola, para a GPU desenhar.

---

## 1. A função de altura

### 1.1 Números aleatórios determinísticos

Tudo parte de `Random(i, j, layer)`. Ela embaralha os bits dos inteiros `i`, `j`, `layer` e da **semente** (`g_TerrainSeed`) com multiplicações e XORs, e devolve um número em [0, 1].

O ponto importante é que **a mesma entrada sempre dá o mesmo número.** Por isso o terreno não precisa ser guardado na memória: qualquer trecho pode ser recalculado a qualquer momento e sai idêntico. Trocar a semente gera outro terreno, e é isso que `Terrain_Reset` faz quando a bola cai da faixa.

### 1.2 Camadas

A altura final é a **soma de 4 superfícies**, as camadas de `g_TerrainLayers`:

| Camada | Retalho | Alturas | Ângulo da grade | Papel |
|---|---|---|---|---|
| 1 | 40 | ±2 | 63° | Regiões mais altas ou mais baixas |
| 2 | 16 | ±3 | 23° | Morros e rampas |
| 3 | 7 | ±0,8 | −40° | Ondulações pequenas |
| 4 | 11 | 0 ou 5,4–9 | 46° | Montanhas íngremes, em 12% dos vértices |

Cada camada é uma grade de vértices espaçados pelo tamanho do retalho, e cada vértice tem uma altura sorteada (`VertexHeight`):
- **camadas comuns:** `amplitude · (2r − 1)`, ou seja, valores entre −amplitude e +amplitude, em torno de 0;
- **camada de montanhas:** se `r < 0,12`, o vértice vira um pico de altura entre 0,6 e 1 vez a amplitude; senão fica em 0. O resultado são picos isolados no meio do relevo.

Como as camadas comuns oscilam em torno de zero, o terreno fica sobre uma linha base y ≈ 0, sem tendência de subir ou descer.

### 1.3 A grade girada

Antes de avaliar uma camada, o ponto (x, z) é girado pelo ângulo dela:

```
xr =  cos·x + sen·z
zr = −sen·x + cos·z
```

Cada camada tem um ângulo diferente, então os morros de uma não se alinham com os eixos nem com os das outras. É isso que tira a aparência de "padrão em grade".

### 1.4 O retalho de Bézier bicúbico

Este é o núcleo, em `AccumulateSurfaceLayer`, e é o conteúdo da Aula 16.

**a) Achar o retalho.** `i = floor(xr/L)`, `j = floor(zr/L)`, e os parâmetros locais são `u = xr/L − i` e `v = zr/L − j`, ambos em [0, 1).

**b) Ler as alturas.** São lidos os 4×4 vértices em volta: os 4 cantos do retalho mais os vizinhos deles.

**c) Estimar as derivadas nos cantos** por diferença central:

```
dH/du = (H(i+1, j) − H(i−1, j)) / 2
dH/dv = (H(i, j+1) − H(i, j−1)) / 2
```

**d) Montar os 16 pontos de controle.** Cada canto define um bloco 2×2:

```
P[0][0] = H                          ← o canto
P[1][0] = H + (dH/du)/3              ← porque a derivada da Bézier no início é 3(P1 − P0)
P[0][1] = H + (dH/dv)/3
P[1][1] = H + (dH/du)/3 + (dH/dv)/3  ← derivada mista nula
```

Nos outros três cantos é igual, com os sinais trocados, apontando para dentro do retalho.

**e) Avaliar** pelo produto tensorial dos polinômios de Bernstein:

```
h(u, v) = Σₖ Σₗ Bₖ(u) · Bₗ(v) · P[k][l]
```

com `B₀ = (1−t)³`, `B₁ = 3t(1−t)²`, `B₂ = 3t²(1−t)` e `B₃ = t³`.

Isso garante **continuidade C1**: dois retalhos vizinhos usam a mesma altura e a mesma derivada em cada vértice que compartilham, então a superfície não tem quinas em lugar nenhum.

### 1.5 Derivadas analíticas

Junto com a altura, a mesma soma calcula `∂h/∂u` e `∂h/∂v`, trocando `B` pela derivada `B'`. Depois disso:
- divide pelo tamanho do retalho (regra da cadeia: `du/dx = 1/L`);
- desfaz a rotação, para ter `∂h/∂x` e `∂h/∂z` no sistema do mundo;
- soma o resultado das 4 camadas, já que a derivada da soma é a soma das derivadas.

O resultado é exposto por `TerrainHeight(x, z)` e `TerrainGradient(x, z)`. A física usa o gradiente para a inclinação na direção do rumo, para a normal e para a distância até a bola.

---

## 2. A malha que a GPU desenha

### 2.1 Faixa e chunks

O terreno é uma **faixa**: infinita em x, mas com largura 48 em z (de −24 a +24). Ela é dividida em **chunks** de 16 de comprimento, e cada chunk cobre a largura toda. Cada chunk é uma grade de 32 × 96 quadriláteros, o que dá um vértice a cada 0,5 unidade.

### 2.2 Montar um chunk

`FillChunk` percorre a grade de vértices do chunk e, para cada um:
- **posição** = `(x, h(x,z), z, 1)`;
- **normal** = `(−∂h/∂x, 1, −∂h/∂z)`, normalizada. É a normal exata da superfície, e não uma média dos triângulos, e é ela que o shader usa na iluminação de Lambert;
- **coordenada de textura** = `(x, z) · 0,25`, a partir da posição no mundo. Com `GL_REPEAT`, a textura continua sem costura de um chunk para o outro.

Os dados vão para a GPU com `glBufferSubData`. Os índices dos triângulos (dois por quadrilátero, em sentido anti-horário visto de cima, por causa do backface culling) são os mesmos para todos os chunks, então são enviados uma única vez.

### 2.3 O buffer circular

Existem só **10 chunks** ao mesmo tempo: 4 atrás da bola e 6 à frente. A cada quadro, `Terrain_Update(x_da_bola)` confere quais trechos deveriam existir. O trecho `k` sempre ocupa a posição `k mod 10` do vetor. Quando a bola avança, o chunk que ficou para trás é **reaproveitado**: seus vértices são recalculados para o trecho novo à frente e reenviados para a GPU. Assim a memória é fixa e o terreno é infinito.

### 2.4 Escondendo a ponta

O fim da área carregada fica a 80–96 unidades à frente. A **neblina** do fragment shader mistura a cor do terreno com a cor do céu entre 35 e 80 unidades da câmera, então a borda nunca aparece.

---

## Resumo do fluxo

```
semente + (i, j, camada) → Random → alturas dos vértices de cada grade
       ↓
ponto (x, z) → girar → achar o retalho → 16 pontos de controle → Bernstein
       ↓
soma das 4 camadas → h(x, z) e ∇h(x, z)
       ↓                                   ↓
física (contato, inclinação, voo)    FillChunk → posições, normais, UVs
                                           ↓
                                     10 chunks circulares → GPU → neblina
```

Para mexer no relevo, basta editar `g_TerrainLayers` em [terrain.cpp:42-48](src/terrain.cpp#L42-L48). O resto se adapta sozinho.

## Passo 1: uma curva de Bézier cúbica (1D)

Uma Bézier cúbica tem **4 pontos de controle**: P0, P1, P2, P3. A curva começa em P0, termina em P3 e é "puxada" por P1 e P2, sem passar por eles.

```
        P1 •          • P2
           ╭──────────╮
          ╱            ╲
     P0 •                • P3
```

Pensando só em altura, cada ponto de controle é um número: P0 = 0, P1 = 3, P2 = 3, P3 = 0. Isso desenha um morrinho. Com P1 e P2 diferentes, a forma muda: mais íngreme no começo, mais suave no fim, e assim por diante.

## Passo 2: emendar várias curvas (o terreno antigo)

Uma curva só cobre um trecho curto. Para um terreno longo, **emendamos várias curvas uma depois da outra**, e o fim de uma é o começo da próxima:

```
  curva 1   curva 2   curva 3   curva 4
 ╭───╮               ╭───╮
╱     ╲             ╱     ╲
       ╲───────────╱       ╲──
|--8--|--8--|--8--|--8--|
```

Cada pedaço, um trecho de 8 unidades com a sua própria curva de 4 pontos, se chama **segmento**. Foi assim que fizemos o primeiro terreno: um perfil desses ao longo de x, "esticado" em z como uma lona.

## Passo 3: de curva para superfície (o "retalho")

Esse perfil só tem relevo em x. Para ter morros que variam **em x e em z ao mesmo tempo**, usamos a versão 2D da Bézier: a **superfície de Bézier bicúbica**.

Em vez de 4 pontos numa linha, ela usa **16 pontos numa grade 4×4**, cobrindo um **quadrado** do chão:

```
  vista de cima, um quadrado do chão:

   P • • • P
   • • • • •
   • • • • •
   P • • • P      ← cada • é um ponto de controle com uma altura
```

Ela funciona como uma curva de Bézier em x combinada com outra em z: em cada direção é a mesma fórmula que você já conhece.

**Retalho é esse quadrado.** O nome vem de *patch* em inglês: é um pedaço de superfície, como um retalho de tecido. O retalho está para a superfície assim como o **segmento** está para a curva:

| 1D (curva) | 2D (superfície) |
|---|---|
| segmento: um trecho de linha | **retalho: um quadrado do chão** |
| 4 pontos de controle | 16 pontos de controle |
| vários segmentos emendados formam o perfil | vários retalhos lado a lado formam o terreno |

Visto de cima, o chão fica dividido num tabuleiro de retalhos, cada um com a sua própria superfície de Bézier. Eles são emendados de forma que não aparece quina na divisa.

```
  vista de cima:
  ┌────┬────┬────┬────┐
  │    │    │    │    │   cada quadrado = 1 retalho
  ├────┼────┼────┼────┤   = 1 superfície de Bézier
  │    │    │    │    │     com 16 pontos de controle
  ├────┼────┼────┼────┤
  │    │    │    │    │
  └────┴────┴────┴────┘
```

**De onde vêm as alturas dos 16 pontos?** Cada canto do tabuleiro recebe uma altura sorteada. Os 16 pontos de controle de um retalho são calculados a partir dos 4 cantos dele e dos vizinhos, de forma que o retalho encaixe suavemente nos do lado.

## Passo 4: camadas

Um tabuleiro só, com quadrados de tamanho 16, já gera morros. Mas os morros ficam todos com **o mesmo tamanho**, e o resultado parece regular.

A solução foi fazer **4 tabuleiros diferentes e somar as alturas**. Cada tabuleiro é uma **camada**:

```
camada 1: quadrados de 40, alturas ±2      ╭──────────────────╮___________   ondas largas
camada 2: quadrados de 16, alturas ±3      ╭──╮___╭─╮____╭───╮___            morros
camada 3: quadrados de 7,  alturas ±0,8    ∿∿∿∿∿∿∿∿∿∿∿∿∿∿∿∿∿∿∿∿∿∿            ondulações
camada 4: quadrados de 11, quase tudo 0    ______╱╲_____________╱╲___        picos raros
                                           ──────────────────────────
soma = terreno final                       relevo irregular, com tudo junto
```

Para saber a altura de um ponto (x, z) do mundo:
1. em cada camada, acha **em qual retalho** o ponto cai;
2. calcula a altura daquela superfície de Bézier ali;
3. **soma** as 4 alturas.

Cada tabuleiro também é **girado** num ângulo diferente. Assim os quadrados de uma camada não se alinham com os da outra, e o resultado não parece uma grade.

---

## Em uma frase

**Bézier cúbica** (curva, 4 pontos) → versão 2D, a **superfície bicúbica** (16 pontos sobre um quadrado = **retalho**) → muitos retalhos lado a lado formam um **tabuleiro** (= **camada**) → **4 camadas** de tamanhos diferentes **somadas** dão o terreno.

## Parte 1: em 1D

### O ponto de partida: alturas sorteadas nos nós

Ao longo do eixo x, a cada L unidades há um **nó** com uma altura sorteada:

```
altura
  5 |                    • H3
  3 |      • H1
  2 |              • H2
  1 | • H0
    +----+-----+-----+-----+--→ x
        0     L    2L    3L
```

Entre dois nós vizinhos colocamos **uma** Bézier cúbica, que é um segmento. O problema é escolher os 4 pontos de controle de cada segmento de forma que os segmentos se emendem sem quina.

### Quina = mudança brusca de inclinação

Dois segmentos que se encontram num nó já têm **a mesma altura** ali, porque os dois passam pelo nó. Isso não basta: se a inclinação de chegada for diferente da de saída, aparece uma quina.

```
   com quina:        sem quina:
      ╱╲               ╭─╮
     ╱  ╲             ╱   ╲
```

Então a regra é esta: **no nó, os dois segmentos têm de ter a mesma inclinação.**

### Como a Bézier controla a inclinação nas pontas

Uma propriedade da Bézier cúbica, vista na aula:
- a inclinação no **início** é dada por `3·(P1 − P0)`;
- a inclinação no **fim** é dada por `3·(P3 − P2)`.

Ou seja, **P1 define a inclinação de saída e P2 define a de chegada.** É por eles que se controla a emenda.

### O truque: cada nó escolhe *uma* inclinação, e os dois lados a usam

Para cada nó `i`, calculamos uma inclinação `Dᵢ` que só depende dos vizinhos dele:

```
Dᵢ = (H(i+1) − H(i−1)) / 2
```

Na prática, é a inclinação da reta que liga o vizinho da esquerda ao da direita. Faz sentido intuitivamente: se o vizinho da frente é mais alto, o terreno está subindo ali.

O segmento do nó `i` até o nó `i+1` usa então:

```
P0 = Hᵢ                    (começa no nó i)
P1 = Hᵢ + Dᵢ/3             → sai com inclinação 3·(Dᵢ/3) = Dᵢ
P2 = H(i+1) − D(i+1)/3     → chega com inclinação 3·(D(i+1)/3) = D(i+1)
P3 = H(i+1)                (termina no nó i+1)
```

No nó `i+1`:
- o segmento da **esquerda** chega com inclinação `D(i+1)`;
- o segmento da **direita** sai com inclinação `D(i+1)`.

**É a mesma inclinação, porque os dois usam o mesmo `D(i+1)`.** Por isso não há quina. Cada segmento é calculado sozinho, mas eles "concordam" porque a inclinação pertence ao nó, e não ao segmento.

### Exemplo com números

Nós: H0 = 1, H1 = 3, H2 = 2, H3 = 5. Segmento do nó 1 ao nó 2:

```
D1 = (H2 − H0)/2 = (2 − 1)/2 = 0,5
D2 = (H3 − H1)/2 = (5 − 3)/2 = 1,0

P0 = 3
P1 = 3 + 0,5/3 = 3,17
P2 = 2 − 1,0/3 = 1,67
P3 = 2
```

### Como a altura é calculada dentro do segmento

Para um x entre os dois nós, calcula-se `t` = a fração do caminho, de 0 a 1. Depois aplica-se a fórmula de Bernstein:

```
h = (1−t)³·P0 + 3t(1−t)²·P1 + 3t²(1−t)·P2 + t³·P3
```

No meio do segmento (t = 0,5) os pesos são 1/8, 3/8, 3/8, 1/8:

```
h = 0,125·3 + 0,375·3,17 + 0,375·1,67 + 0,125·2 = 2,44
```

O resultado é coerente: está entre 3 e 2, um pouco mais alto porque o terreno ainda vinha subindo em H1.

## Parte 2: em 2D (o retalho)

Agora os nós formam uma **grade** no chão, e cada nó tem uma altura sorteada. Um retalho é o quadrado entre 4 nós vizinhos.

```
  vista de cima:
  H(i,j+1) ●───────● H(i+1,j+1)
           │       │
           │retalho│
           │       │
  H(i,j)   ●───────● H(i+1,j)
```

### Inclinações: agora são duas por nó

Cada nó tem uma inclinação **na direção x** e outra **na direção z**, calculadas do mesmo jeito, pelos vizinhos:

```
Du = (H(i+1,j) − H(i−1,j)) / 2      ← vizinhos da esquerda e da direita
Dv = (H(i,j+1) − H(i,j−1)) / 2      ← vizinhos de trás e da frente
```

### Os 16 pontos de controle

Cada um dos 4 cantos fornece um **bloquinho de 2×2** pontos:

```
  canto + Dv/3      canto + Du/3 + Dv/3
       •─────────────•
       │             │
       •─────────────•
     canto        canto + Du/3
```

- o próprio canto, que é a altura do nó;
- um ponto "puxado" em x pela inclinação Du, como o P1 do caso 1D;
- um ponto "puxado" em z pela inclinação Dv;
- um ponto puxado nas duas direções.

Os 4 cantos × 4 pontos dão os 16 pontos de controle.

### Por que não há quina entre retalhos

Pegue a **borda** comum entre dois retalhos vizinhos. Ao longo dela, a superfície vira exatamente a curva 1D da Parte 1, e essa curva só depende dos **dois nós nas pontas da borda**: as alturas e as inclinações deles. Os dois retalhos compartilham esses dois nós, então:
- **a altura ao longo da borda é a mesma** dos dois lados, ou seja, não abre buraco;
- **a inclinação atravessando a borda também é a mesma**, porque vem das inclinações dos mesmos dois nós, ou seja, não há quina.

É o mesmo princípio do 1D: **as inclinações pertencem aos nós, e quem compartilha nós concorda.**

### Como a altura é calculada dentro do retalho

Com o ponto (x, z), achamos o retalho e as frações `u` (em x) e `v` (em z), ambas entre 0 e 1. A altura sai fazendo **Bézier duas vezes**:

```
  16 pontos (4 linhas de 4)
        │
        ▼  Bézier em u em cada linha
  4 números
        │
        ▼  Bézier em v com esses 4 números
  1 número = a altura
```

1. Cada uma das 4 linhas de pontos de controle é uma curva cúbica em x. Avaliando cada uma em `u`, saem 4 números.
2. Esses 4 números viram os pontos de controle de uma última curva, em z. Avaliando em `v`, sai a altura.

No código isso aparece como uma soma dupla, `Σₖ Σₗ Bₖ(u)·Bₗ(v)·P[k][l]`, mas é a mesma conta.

## Por que emendar

Uma Bézier cúbica só tem 4 pontos de controle, e com eles não dá para fazer formas longas ou complexas. Subir o grau (10, 20 pontos) deixa a curva difícil de controlar: mexer num ponto altera a curva inteira. Por isso o padrão é emendar **várias cúbicas em sequência**, como vimos na aula de Curvas e Superfícies.

```
   curva A                curva B
A0 ●──A1•──A2•──● A3 = B0 ──B1•──B2•──● B3
```

A qualidade da emenda depende de quais condições se impõem no ponto de junção. São três níveis.

---

## Nível 1: continuidade C0 (só encostar)

**Regra:** o último ponto de A é o primeiro de B, ou seja, `A3 = B0`.

```
          A2•    •B1
            ╲   ╱
     ╭───────●───────╮     ← as curvas se tocam,
    ╱       A3=B0     ╲       mas formam um "bico"
```

A curva não tem buraco, mas pode ter uma **quina**: A chega numa direção e B sai em outra. Era o que acontecia nos lábios das rampas, que eram C0 de propósito.

---

## Nível 2: continuidade C1 (sem quina)

**Regra:** além de `A3 = B0`, a **tangente** na chegada de A tem de ser igual à tangente na saída de B.

Usando a propriedade da Bézier:
- a tangente no fim de A é `3·(A3 − A2)`;
- a tangente no início de B é `3·(B1 − B0)`.

Igualando as duas:

```
A3 − A2 = B1 − B0
```

Geometricamente: **A2, o ponto de junção e B1 ficam alinhados, e o ponto de junção fica exatamente no meio do segmento entre A2 e B1.**

```
     A2 •───────●───────• B1      ← colineares e equidistantes
              A3 = B0
     ╭──────────●──────────╮      ← a curva passa suave
```

Dessa forma, quem chega e quem sai têm a mesma direção e a mesma velocidade.

**Consequência prática:** ao editar uma curva emendada num programa de desenho, mover A2 obriga a mover B1 para o lado oposto, para manter C1. É a "alça" que gira em torno do nó, como no Illustrator ou no Inkscape.

---

## Nível 2b: continuidade G1 (geométrica)

**Regra:** A2, o ponto de junção e B1 continuam **alinhados**, mas a distância de cada lado pode ser diferente.

```
  A2 •────●──────────────• B1     ← colineares, distâncias diferentes
```

Visualmente também não há quina, porque a direção é a mesma, mas a "velocidade" com que a curva passa pelo ponto muda. É menos restritivo que C1.

---

## Nível 3: continuidade C2 (curvatura também igual)

Também iguala a segunda derivada, ou seja, a curvatura. Exige uma relação entre A1, A2, B1 e B2. Isso é o que as **B-splines** garantem automaticamente. Para o nosso caso C1 basta, porque a física só usa altura e inclinação.

---

## Onde isso aparece no nosso terreno

O terreno é uma sequência de cúbicas emendadas com **C1**. A diferença está em **como escolher** A2 e B1 para que fiquem alinhados com o nó:

| Versão do terreno | Como escolhemos A2 e B1 | Resultado |
|---|---|---|
| Primeira (ondas) | `A2 = A3` e `B1 = B0`: os três pontos na mesma altura | C1 com tangente **horizontal** em todo nó, por isso topos e vales eram "achatados" |
| Rampas com lábio | Na subida, A2 abaixo do lábio; na descida, B1 também abaixo | **Só C0** no lábio (a quina proposital) |
| **Atual** | `A2 = nó − D/3` e `B1 = nó + D/3`, com o mesmo D | C1 com tangente **qualquer**: o nó fica no meio, alinhado, que é exatamente a regra do nível 2 |

O `D = (vizinho da direita − vizinho da esquerda)/2` da explicação anterior é só uma forma automática de escolher a direção da alça em cada nó. Com essa escolha, a regra "A2, nó e B1 alinhados e equidistantes" é cumprida por construção.

## A ideia em uma frase

**A direção em que uma Bézier começa ou termina é dada pelo ponto de controle vizinho da ponta.** Para emendar duas curvas sem quina, os pontos vizinhos da emenda, um de cada lado, precisam formar uma **linha reta** passando pela emenda.

## Exemplo

Considere duas curvas, A e B. Cada uma tem 4 pontos de controle, espaçados igualmente em x, e cada número abaixo é uma altura. **A emenda é onde A termina e B começa**, ou seja, o último ponto de A é o primeiro de B.

**Curva A:** `0, 1, 2, 3`

Os pontos sobem de 1 em 1. A curva A **termina subindo**, e quem define essa subida final é o penúltimo ponto (2) indo para o último (3): sobe 1.

**Curva B**, que começa em 3 porque começa onde A termina: o que interessa é o **segundo ponto** dela, porque ele define como B **começa**.

### Caso 1: B = `3, 3, ...`  →  QUINA

```
altura
  3 |       ●───●          ← A chegou subindo,
  2 |     ●                  B saiu reto
  1 |   ●
  0 | ●
```

A chegou **subindo** (de 2 para 3), mas B sai **reto** (de 3 para 3). A direção muda de repente, e isso é a quina.

### Caso 2: B = `3, 4, ...`  →  SEM QUINA

```
altura
  4 |           ●          ← B continua subindo
  3 |       ●                 do mesmo jeito
  2 |     ●
  1 |   ●
  0 | ●
```

A chegou subindo 1 (de 2 para 3), e B sai subindo 1 (de 3 para 4). É a mesma direção, então não há quina.

Olhe só **três pontos**: o penúltimo de A, a emenda e o segundo de B.

```
penúltimo de A  →  emenda  →  segundo de B
       2        →     3    →       4         ✓ linha reta: sem quina
       2        →     3    →       3         ✗ dobra: quina
```

Se esses três estiverem em linha reta, sem dobra, a emenda é suave. **Só isso.** O resto dos pontos de cada curva pode ser qualquer coisa.

- o penúltimo ponto da curva da esquerda **um pouco abaixo** da emenda;
- o segundo ponto da curva da direita **um pouco acima** dela, na mesma medida.

Assim os três pontos sempre ficam alinhados, e o terreno nunca tem quina.

----- CLAUDE [2026-11-01 20:53:20] -----
Sim, na curva 1D isso define a inclinação numa direção só, a da própria curva. É por isso que, no retalho 2D, **cada nó tem duas inclinações**:

- **Du:** a inclinação na direção x, calculada pelos vizinhos da esquerda e da direita;
- **Dv:** a inclinação na direção z, calculada pelos vizinhos de trás e da frente.

E a lógica de "penúltimo de A, emenda, segundo de B" é aplicada **nas duas direções**, separadamente:

```
  vista de cima, ao redor de um nó ● :

                 ○  ← nó + Dv/3   (puxado em z, usa Dv)
                 │
    ○ ─────────  ●  ───────── ○
  nó − Du/3     nó      nó + Du/3   (puxados em x, usam Du)
                 │
                 ○  ← nó − Dv/3
```

- **Na direção x,** os pontos de controle vizinhos do nó ficam em `nó ± Du/3`. Isso garante que, andando em x, não há quina ao passar do retalho da esquerda para o da direita.
- **Na direção z,** os vizinhos ficam em `nó ± Dv/3`. Isso garante o mesmo andando em z, entre o retalho de trás e o da frente.

Sobra um ponto por canto, o da diagonal (`nó + Du/3 + Dv/3`). Ele é puxado nas duas direções ao mesmo tempo e serve para a inclinação variar suavemente **ao longo** da borda, e não só nos cantos.

Então são duas regras de emenda independentes, uma para cada eixo, e as duas usam as inclinações que pertencem ao nó. Juntas, deixam o retalho sem quina em qualquer direção.

----- CLAUDE [2026-11-01 20:53:46] -----
A regra só é necessária **entre retalhos** (inter). **Dentro de um retalho** (intra), a superfície já é lisa por natureza.

## Dentro de um retalho: nunca há quina

A Bézier é um **polinômio**, e polinômios são suaves em todo ponto, quaisquer que sejam os pontos de controle. Os 16 pontos de um retalho podem ter as alturas que for: a superfície dentro dele nunca terá quina. Os pontos internos não precisam estar alinhados entre si.

## Entre retalhos: é aí que a regra atua

Quina só pode aparecer na **borda**, onde termina um polinômio e começa outro. É ali que entra a regra do alinhamento, e os pontos alinhados ficam **em retalhos diferentes**:

```
        retalho da esquerda  │  retalho da direita
                             │
   ...    ○         ○        ●        ○         ○    ...
                nó − Du/3    nó   nó + Du/3
                    ↑               ↑
         pertence ao retalho   pertence ao retalho
             da esquerda          da direita
```

- **`nó − Du/3`** é o **penúltimo** ponto de controle do retalho da esquerda.
- **`nó`** é o canto, compartilhado pelos dois.
- **`nó + Du/3`** é o **segundo** ponto de controle do retalho da direita.

É exatamente o "penúltimo de A, emenda, segundo de B", com A e B sendo dois retalhos vizinhos. Na direção z vale o mesmo com Dv, entre o retalho de trás e o da frente.

## Resumo

| Onde | Precisa da regra? | Por quê |
|---|---|---|
| **Dentro** do retalho | Não | É um polinômio, sempre liso |
| **Na borda** entre retalhos | Sim | Dois polinômios se encontram; a regra alinha os pontos dos dois lados |

Cada retalho só guarda o próprio lado. É o fato de **os dois lados serem calculados a partir do mesmo nó** que faz eles concordarem na borda.

Porque a inclinação no começo de uma Bézier cúbica é **3 vezes** a diferença entre os dois primeiros pontos de controle:

```
inclinação no início = 3 · (P1 − P0)
```

Queremos que essa inclinação seja `Du`, então:

```
3 · (P1 − P0) = Du    →    P1 − P0 = Du / 3    →    P1 = P0 + Du/3
```

Por isso aparece `Du/3`. No fim da curva vale o mesmo: `inclinação = 3 · (P3 − P2)`, e por isso `P2 = P3 − Du/3`.

## De onde vem esse 3

A fórmula da cúbica é:

```
B(t) = (1−t)³·P0 + 3t(1−t)²·P1 + 3t²(1−t)·P2 + t³·P3
```

Derivando em `t` e calculando em `t = 0`, os termos com P2 e P3 somem, porque têm t² e t³, e sobra:

```
B'(0) = −3·P0 + 3·P1 = 3·(P1 − P0)
```

O 3 vem do grau da curva. Numa Bézier quadrática seria 2, e numa de grau n seria n.

## Conferência intuitiva: uma reta

Considere nós com alturas `0, 1, 2, 3`, uma subida reta, com 1 de altura por retalho. Para o segmento do nó 0 ao nó 1:

pontos de controle:  0,   0 + 0,33,   1 − 0,33,   1
                  =  0,     0,33,       0,67,     1

Os pontos ficam **igualmente espaçados**, em 1/3 e 2/3 do caminho, e uma Bézier com pontos assim é exatamente uma **reta**. Está certo.

`Du = (H(i+1) − H(i−1)) / 2` é a inclinação medida **por retalho**: quanto a altura muda ao andar um retalho inteiro. A divisão por 2 aparece porque de `i−1` a `i+1` são dois retalhos. No chão, a bola não pode cair, porque o terreno a segura. Só sobra a parte da gravidade que **puxa ladeira abaixo**, e essa parte muda a **velocidade** dela.

```
            ↘ parte que acelera (ao longo da rampa)
     ●
      ╲  ↓ gravidade total
       ╲
        ╲  ← rampa
         ╲   ↙ parte anulada pelo chão (perpendicular à rampa)
```

### Passo a passo (`UpdatePlayerOnGround`)

**a) A inclinação na direção em que a bola anda.** O terreno tem inclinação em x e em z (o gradiente). Mas só interessa a inclinação na direção do rumo da bola:

```cpp
slope = dh/dx · cos(rumo) + dh/dz · (−sen(rumo))
```

`slope > 0` é subida, `slope < 0` é descida e `slope = 0` é plano. Por isso **virar muda a inclinação que a bola sente**: andar de lado numa encosta é quase plano.

**b) A parte da gravidade ao longo da rampa:**

```cpp
gravity_acceleration = −gravity · slope / √(1 + slope²)
```

O termo `slope / √(1 + slope²)` é o seno do ângulo da rampa. Então:
- **descida:** aceleração positiva, a bola ganha velocidade;
- **subida:** aceleração negativa, a bola perde velocidade;
- **plano:** zero.

Com dive a gravidade é 24 em vez de 7,2, então **tudo fica 3,3 vezes mais intenso**: acelera mais na descida e freia mais na subida.

**c) O arrasto,** que tira um pouco do excesso acima do piso:

```cpp
drag_acceleration = −0,01 · (velocidade − 5)
```

Ele é muito fraco (meia-vida de cerca de 70 s). Serve só para impedir que a velocidade cresça para sempre.

**d) O piso:** a velocidade nunca fica abaixo de 5.

```cpp
g_PlayerSpeed = max(g_PlayerSpeed, 5);
```

### Exemplo numa descida de 20°

seno(20°) ≈ 0,34:
- sem dive: 7,2 × 0,34 = **+2,4** u/s por segundo;
- com dive: 24 × 0,34 = **+8,2** u/s por segundo.

Numa subida de 20° os sinais se invertem. Por isso o ritmo do jogo é **dive na descida, soltar na subida**.

---

## 3. No ar: a gravidade age **na vertical**

No ar não há chão para anular nada, então a gravidade age inteira, para baixo. Ela não muda a velocidade horizontal (`VH`, constante no voo), só a vertical (`VY`).

### Planando (sem dive): entra a sustentação

`PlayerAirGravity` desconta uma **sustentação**, como a de uma asa, **somente enquanto a bola desce**:

```cpp
if (diving || VY >= 0)  return gravity;            // subindo ou com dive: gravidade inteira
lift = 0,022 · VH²;                                 // cresce com a velocidade horizontal
return gravity − min(lift, 0,8 · gravity);          // no máximo 80% da gravidade
```

| Velocidade horizontal | Gravidade efetiva na descida (sem dive) |
|---|---|
| 5 | 7,2 − 0,55 = **6,65** |
| 10 | 7,2 − 2,2 = **5,0** |
| ≥ 12,1 | 7,2 − 5,76 = **1,44** (limite) |

Ou seja: **rápido, a bola plana longe; devagar, cai pesado.** Ela nunca para de cair, porque a sustentação vai no máximo até 80%.

**Por que só na descida:** se a sustentação agisse também na subida, em alta velocidade a bola subiria alto demais. Ela amortece a queda, mas não empurra a bola para cima.

### Com dive: mergulho

Gravidade de 24, sem sustentação. A bola cai rápido, e é assim que se volta para o chão para pegar a próxima descida.

### A trajetória

Com aceleração constante, o código usa a fórmula exata:

```cpp
Y  += VY·dt − ½·g·dt²
VY −= g·dt
```

O resultado é uma **parábola**. No topo do voo, quando a sustentação entra, viram duas parábolas emendadas: a da descida é mais aberta.

---

## 4. A passagem entre chão e ar

**Decolagem.** No chão, a cada quadro o código pergunta: "se a bola estivesse solta, sujeita só à gravidade do ar, ela ainda tocaria o terreno no próximo instante?" Se a resposta for não, ela decola. Isso acontece quando o terreno **se curva para baixo mais rápido do que a bola cai**, como no topo de um morro em alta velocidade. Também é preciso estar pelo menos 0,5 acima do piso de velocidade, para que a velocidade mínima sozinha nunca decole a bola.

**Pouso.** No ar, quando a bola encosta no terreno **e está se aproximando dele**, a velocidade é dividida em duas partes:
- a parte **ao longo da rampa** é mantida e vira a nova velocidade no chão;
- a parte **contra o chão** é absorvida.

Então **pousar alinhado com uma descida** mantém quase toda a velocidade, e **pousar de frente para uma subida** perde quase tudo.

Na decolagem **nada é perdido nem absorvido**. É o contrário do pouso: a velocidade só é **reescrita em duas partes**, horizontal e vertical, e as duas viram a velocidade do voo.

## No chão, a velocidade é uma seta ao longo da rampa

No chão, o código guarda **um número só**: `g_PlayerSpeed`, a velocidade ao longo do terreno. A direção é a da rampa:

```
                  ↗ velocidade (ao longo da rampa)
                 ╱
          ●     ╱  ← rampa subindo
               ╱
```

## Na decolagem, essa seta é dividida em duas partes

```
                  ↗  velocidade total
                 ╱│
                ╱ │  VY = parte vertical (para cima)
               ╱θ │
              ──────
              VH = parte horizontal (para a frente)
```

É a decomposição de um vetor num triângulo retângulo:
- **horizontal:** `VH = velocidade · cos θ`
- **vertical:** `VY = velocidade · sen θ`

onde θ é o ângulo da rampa no ponto da decolagem.

No código ([main.cpp](src/main.cpp), `UpdatePlayerOnGround`) é a mesma conta, escrita com a inclinação (`slope = tan θ`) em vez do ângulo:

```cpp
float vh = g_PlayerSpeed / len;           // = velocidade · cos θ
float vy = g_PlayerSpeed * slope / len;   // = velocidade · sen θ
// len = √(1 + slope²)
```

Quando a bola decola, essas duas partes são copiadas para o voo:

```cpp
g_PlayerVH = vh;
g_PlayerVY = vy;
```

## Exemplo com velocidade 10

| Terreno no ponto de decolagem | Inclinação | VH (frente) | VY (vertical) |
|---|---|---|---|
| Subindo (~27°) | +0,5 | 8,9 | **+4,5** (sai subindo) |
| Topo plano | 0 | 10 | **0** (sai na horizontal) |
| Descendo (~17°) | −0,3 | 9,6 | **−2,9** (sai já descendo) |

Nos três casos √(VH² + VY²) = 10: a velocidade total é a mesma, só muda a direção.

## O que acontece depois

- **VH** fica **constante** durante todo o voo.
- **VY** muda com a gravidade: diminui até zero, que é o topo do voo, e depois fica negativa, que é a queda.

Na prática, a decolagem quase sempre acontece **perto do topo de um morro**, onde o terreno começa a se curvar para baixo. Ali a inclinação é pequena, e por isso a bola costuma sair quase na horizontal, com VY pequeno.

O cálculo é uma **projeção**: o código mede "quanto da velocidade da bola aponta na mesma direção da rampa". Vou montar a conta em três passos, com números.

## Passo 1: a velocidade da bola no ar

No momento do pouso, a bola tem duas componentes:

```
VH = 10   (para a frente)
VY = −6   (para baixo)
```

Como seta: `v = (10, −6)`. O tamanho dela é √(10² + 6²) ≈ **11,7**.

## Passo 2: a direção da rampa

A rampa tem inclinação `slope`, ou seja, sobe `slope` a cada 1 andado para a frente. A direção dela é a seta `(1, slope)`.

Para usar só a **direção**, a seta é dividida pelo próprio tamanho, `len = √(1 + slope²)`, e vira uma seta de tamanho 1:

```
direção da rampa = (1, slope) / len
```

## Passo 3: a projeção (produto escalar)

A parte da velocidade que fica **ao longo da rampa** é o produto escalar da velocidade com a direção da rampa:

```
v_along = v · direção
        = (VH, VY) · (1, slope) / len
        = (VH · 1  +  VY · slope) / len
```

Essa é exatamente a linha do código:

```cpp
float v_along = (g_PlayerVH + g_PlayerVY*slope) / len;
```

A **redução** é a diferença entre o tamanho total (11,7) e `v_along`. Essa diferença é a parte perpendicular, que o chão absorve.

## Os três casos, conta por conta

**Descida com slope = −0,6:**
```
len     = √(1 + 0,36)            = 1,166
v_along = (10 + (−6)·(−0,6)) / 1,166
        = (10 + 3,6) / 1,166     = 11,7
redução = 11,7 − 11,7            = 0      ← seta alinhada com a rampa
```

**Plano, slope = 0:**

v_along = (10 + (−6)·0) / 1      = 10
redução = 11,7 − 10              = 1,7    ← perdeu a parte vertical
```

**Subida com slope = +0,6:**

v_along = (10 + (−6)·0,6) / 1,166
        = (10 − 3,6) / 1,166     = 5,5
redução = 11,7 − 5,5             = 6,2    ← seta quase contra a rampa
```

## Por que o `VY · slope` faz a diferença

O termo `VY · slope` decide tudo:
- **caindo numa descida:** VY e slope são negativos, o produto é **positivo** e a queda **ajuda**;
- **no plano:** slope = 0, e a queda não conta nem a favor nem contra;
- **caindo numa subida:** o produto é **negativo** e a queda **atrapalha**.

Por último, `g_PlayerSpeed = max(v_along, 5)` garante que, mesmo no pior pouso, a bola não fica abaixo do piso de velocidade.
